# Evidence behind Code Comments

Primary research reviewed 2026-10-02. This is an annotated evidence review,
not an exhaustive systematic review or proof that this skill improves
maintenance outcomes. Full papers were inspected except [R5], for which the
primary publisher abstract was available. Summaries are original prose.

The research supports asking whether a comment supplies accurate information
the reader needs. It does not establish a universal comment density, a
“why-only” rule, a guaranteed comprehension benefit, or a causal bug-reduction
percentage. Samples, languages, tasks, and quality definitions differ. Editorial
choices below are practical inferences; language syntax comes from the separate
[conventions guide](language-conventions.md).

## Findings mapped to decisions

| Decision | Evidence | Limit on the inference |
| --- | --- | --- |
| Preserve useful clarification and rationale from review | R1, R4 | Review intent and a quality model do not prove causal benefit |
| Check claims against current code and callers | R2, R5, R6 | Associations and edit patterns do not certify semantic consistency |
| Add information selectively, without a density target | R4, R7, R8 | Small-task experiments do not settle documentation needs in large systems |
| Make TODOs actionable; preserve unresolved constraints | R3, R9, R10 | Wording does not guarantee resolution; comment removal is not debt repayment |
| Inspect generated prose rather than trusting fluency or scores | R11, R12 | Studied models and tasks do not estimate current harness error rates |
| Help humans inspect generated code with concise, locally anchored explanations | R13, R14, R15 | Only R15 tested an explanation intervention; it used transient UI overlays |
| Optimize for understanding rather than persuasive acceptance | R16 | Adoption is not comprehension or review correctness |

## Human review of generated code

This is the plugin's primary use case: a human reviewing code they did not
write, often generated by an LLM. The studies below address that situation.
Keep this evidence separate from R11-R12, which assess generated comments.
Explanation can be useful while its content still needs independent checking.

### R13. Understanding, editing, and debugging generated blocks

Vaithilingam, Zhang, and Glassman (2022),
[Expectation vs. Experience: Evaluating the Usability of Code Generation Tools Powered by Large Language Models](https://glassmanlab.seas.harvard.edu/papers/copilot_lbw_chi22.pdf).

**Method:** A counterbalanced study of 24 programmers, mostly university
students, completing short Python tasks with Copilot versus IntelliSense.
**Result:** Completion-time and success differences were not significant;
observations and interviews identified difficulties understanding, editing,
and debugging generated blocks despite widespread preference for Copilot.
**Limit:** Early tool, small mostly academic sample, three bounded tasks.
Explanatory inline comments were future work, not the tested intervention.
**Application:** Explain purpose, unfamiliar behavior, assumptions, and failure
boundaries so a human can inspect the generated block. This study does not
prove that source comments improve review correctness.

### R14. Exploration and generation prompts

Barke, James, and Polikarpova (2023),
[Grounded Copilot: How Programmers Interact with Code-Generating Models](https://shraddhabarke.github.io/raw/copilot.pdf).

**Method:** Grounded-theory observation of 20 participants across four
languages, quantitative behavioral analysis, and five supplementary
livestreams. **Result:** Programmers alternated between accelerating a known
plan and exploring unfamiliar APIs/algorithms. Exploration involved closer
inspection and documentation reading; generation prompts and maintainable
documentation served different purposes. **Limit:** Mostly academic sample,
designed tasks, 11 first-time Copilot users, early tool; observational.
**Application:** Turn useful generation intent into verified explanations of
the resulting data flow, API semantics, and constraints. A prompt left in
source is not evidence that the generated implementation meets it.

### R15. Explanations beside just-generated code

Yan, Hwang, Wu, and Head (2024),
[Ivie: Lightweight Anchored Explanations of Just-Generated Code](https://andrewhead.info/assets/pdf/ivie.pdf).

**Method:** A counterbalanced lab comparison with 32 programmers, mostly
graduate students, on short OpenCV tasks. Ivie placed compact explanations
beside expressions/blocks; an editor chatbot was the baseline. Both explanation
tools used GPT-3.5. **Result:** Ivie improved unfamiliar-API comprehension
answers and response time; participants favored concise local explanations.
**Limit:** Narrow tasks and population; placement, timing, granularity, and
interaction changed together. The study tested transient editor explanations,
not durable source comments or defect detection. **Application:** Keep useful
explanations close to the meaningful unit: transformations, parameter roles,
unfamiliar semantics, and constraints. Put durable rationale in source; do not
bury the implementation in temporary teaching prose.

### R16. Adoption is a different outcome

Li, Treude, and Turel (2025 preprint),
[Do Comments and Expertise Still Matter? An Experiment on Programmers' Adoption of AI-Generated JavaScript Code](https://arxiv.org/html/2503.11453v1).

**Method:** An online experiment with 173 valid responses from 251 recruits,
five LeetCode tasks, and GPT-4 solutions with or without comments. Adoption
was measured by code similarity excluding comments. **Result:** Commented
solutions predicted greater adoption; expertise and its interaction were not
significant. **Limit:** Adoption was measured, not understanding or review
accuracy. All solutions passed the task tests, and commented/uncommented code
came from separate generation prompts rather than an identical-code
comment-only treatment. **Application:** Help a reviewer explain and assess
actual behavior. Do not optimize comments for reassurance or acceptance.

## Source-comment maintenance and quality

### R1. Comments in code review

Rao, Tsay, Hirzel, and Hellendoorn (2022),
[Comments on Comments: Where Code Review and Documentation Meet](https://arxiv.org/html/2204.00107).

**Method:** Mining approximately 700,000 review comments in 2,000 Java/Python
projects; a taxonomy from 240 manually examined cases, with 134 relevant to
documentation. **Result:** Clarification was the dominant intent in the relevant
sample; reviews also addressed inaccurate, redundant, and newly outdated
comments. **Limit:** Observational data, imperfect selection filters, and a
small taxonomy sample. The frequencies are not universal estimates.
**Application:** Preserve explanations a future maintainer would otherwise have
to rediscover. A code-review conversation may contain useful context, but
verify it before moving it into source.

### R2. Inconsistency and bug-introducing changes

Radmanesh, Imani, Ahmed, and Moshirpour (2024),
[Investigating the Impact of Code Comment Inconsistency on Bug Introducing](https://arxiv.org/html/2409.10781v1).

**Method:** GPT-3.5 inconsistency labels, GitCProc/SZZ bug labels, and temporal
odds-ratio analysis in eight Apache Java repositories. **Result:** Classified
inconsistencies were associated with greater odds of bug-introducing changes,
especially recent inconsistencies. **Limit:** Classifier error, bug-label
proxies, selected repositories, and confounding. Odds are not probabilities,
and association is not causation. **Application:** Review nearby comment claims
when behavior changes. Do not claim a quantified bug-prevention benefit or
generalize the result directly to every language.

### R3. TODO quality and lifecycle

Wang, Gao, Bi, Grundy, Wang, Wu, and Yang (2024; arXiv upload 2025),
[What Makes a Good TODO Comment?](https://zpgao.github.io/papers/what_makes_a_good_todo_comment.pdf),
[publication record](https://research.monash.edu/en/publications/what-makes-a-good-todo-comment/),
DOI `10.1145/3664811`.

**Method:** Manual classification of 2,863 introduced TODOs from 53 repositories
remaining after filtering a top-100 Java repository pool, with lifecycle and
classifier analysis. **Result:** Under the authors' criteria, task TODOs need a
specific actionable task; notice TODOs need a clear situation and problem or
potential task. Overall resolution proportions and lifecycle commit counts
did not differ significantly. **Limit:** Author-defined quality, Java sample,
observational comparisons. **Application:** Keep enough local context to act,
even with an issue link. Do not claim that good wording makes work get resolved.

### R4. Comment categories and quality

Steidl, Hummel, and Juergens (2013),
[Quality Analysis of Source Code Comments](https://teamscale.com/publications/2013-quality-analysis-of-source-code-comments.pdf).

**Method:** Java/C++ comment classification and a category-specific quality
model, a survey of 16 experienced developers, and a five-project case study.
**Result:** Different categories need different assessment; raw comment ratios
hide consistency, completeness, coherence, and usefulness. **Limit:** Heuristic
metrics require inspection and are not a complete quality score or reliable
project ranking. **Application:** Density alone cannot assess accuracy or
usefulness. Do not turn the paper's length heuristics into universal lint rules.

### R5. Comment/code co-evolution

Fluri, Würsch, Giger, and Gall (2009),
[Analyzing the co-evolution of comments and source code](https://link.springer.com/article/10.1007/s11219-009-9075-x).

**Method:** Heuristic comment-to-entity mapping and history analysis across
eight open/closed-source systems. **Result:** Comment and code changes often
coincided; API changes could also be documented in later revisions.
**Limit:** Only the primary abstract was inspected. Change timing does not
measure semantic accuracy or establish a general maintenance benefit.
**Application:** Check documentation while the behavior change's context is
available. An accompanying comment edit is not evidence of correctness.

### R6. Update patterns and bugs

Ibrahim, Bettenburg, Adams, and Hassan (2012),
[On the Relationship between Comment Update Practices and Software Bugs](https://sail.cs.queensu.ca/data/pdfs/JSS_OnTheRelationshipBetweenCommentUpdatePracticesAndSoftwareBugs.pdf).

**Method:** Historical function-level code/comment update models and future bug
analysis in FreeBSD, PostgreSQL, and Eclipse. **Result:** Deviations from usual
update patterns were informative; unmatched code/comment edits did not always
correlate with more bugs. **Limit:** An inconsistent edit pattern is not
necessarily an incorrect statement; correlations are not causal.
**Application:** Update comments whose meaning changed. Do not force a comment
edit with every code edit or treat a comment-only correction as a defect.

### R7. Small maintenance tasks

Nielebock, Krolikowski, Krüger, Leich, and Ortmeier (2019),
[Commenting Source Code: Is It Worth It For Small Programming Tasks?](https://jacobkrueger.github.io/assets/papers/Nielebock2019Comments.pdf).

**Method:** An online experiment with 277 participants, including 227
professionals, solving nine small Java maintenance tasks under no-comment,
implementation-comment, or documentation-comment conditions. **Result:** Time
and correctness benefits were sporadic; professional performance effects were
generally negligible despite favorable opinions. **Limit:** Small algorithmic
examples, German-language tasks/comments, and unsupervised participation.
**Application:** Avoid routine paraphrases of readable private code. This does
not justify removing public contracts or domain context in unfamiliar systems.

### R8. Reading strategies and comprehension

Abdelsalam, Peitek, Bergum, and Apel (2026),
[The Effect of Comments on Program Comprehension: An Eye-tracking Study](https://link.springer.com/article/10.1007/s10664-025-10721-2).

**Method:** A counterbalanced within-subject study with 20 computer-science
students and 12 Java snippets, using correctness, time, eye movements, and
qualitative feedback. **Result:** Comments changed attention and reading
strategies; performance effects varied by snippet, and positive perceptions
did not consistently track better performance. **Limit:** Small student sample,
controlled snippets, altered identifiers, and a combined performance measure.
**Application:** Address the intended reader's uncertainty. More prose and
positive subjective ratings are insufficient evidence of quality.

### R9. Self-admitted technical debt

Potdar and Shihab (2014),
[An Exploratory Study on Self-Admitted Technical Debt](https://users.encs.concordia.ca/~eshihab/pubs/Potdar_ICSME2014.pdf).

**Method:** Manual inspection of 101,762 comments from Eclipse, Chromium OS,
Apache HTTP Server, and ArgoUML, followed by pattern-based history analysis.
**Result:** Admissions of workarounds and incomplete work occurred across
projects and could persist over releases. **Limit:** Four projects, selection
heuristics, and comment persistence/removal as imperfect debt proxies.
**Application:** Preserve useful constraints and unresolved work. Verify the
implementation before removing a debt comment; deletion does not prove repair.

### R10. Inline comment smells

Jabrayilzade, Yurtoğlu, and Tüzün (2024),
[Taxonomy of inline code comment smells](https://link.springer.com/article/10.1007/s10664-023-10425-5).

**Method:** A multivocal literature review, manual labels for 2,447 comments in
four Java/four Python projects, a 41-practitioner survey, and proposed fixes.
**Result:** Eleven categories captured recurring problems, with practitioner
disagreement about some categories and value attributed to some task and
formatting comments. **Limit:** Taxonomy and opinion do not establish harm for
every instance; proposed fixes had limited acceptance. **Application:** Use
smells as inspection prompts. Do not automatically delete TODOs, separators,
or any other category without understanding its purpose and local convention.

### R11. Evaluating generated summaries

Mastropaolo, Ciniselli, Di Penta, and Bavota (2024; preprint 2023),
[Evaluating Code Summarization Techniques: A New Metric and an Empirical Characterization](https://arxiv.org/html/2312.15475v1).

**Method:** Forty metrics compared with 5,201 developer evaluations of generated
Java-method summaries, including a proposed code-aware metric, SIDE.
**Result:** Similarity to reference text alone misses whether a summary suits
the code; code-aware assessment supplies complementary information.
**Limit:** Dataset/model/task limits; SIDE also disagreed with human judgments
in examples. **Application:** Check generated prose against behavior and reader
needs. No automatic score, old comment, or fluent phrasing certifies truth.

### R12. Multilingual generated comments

Katzy, Huang, Panchu, Ziemlewski, Loizides, Vermeulen, van Deursen, and Izadi
(2025), [A Qualitative Investigation into LLM-Generated Multilingual Code Comments and Automatic Evaluation Metrics](https://arxiv.org/html/2505.15469v1).

**Method:** Expert labels for 12,500 generations from five code models across
Chinese, Dutch, English, Greek, and Polish, with an error taxonomy and metric
evaluation. **Result:** Outputs had informativeness, language, and syntax
errors; tested metrics did not reliably distinguish correct and incorrect
outputs. **Limit:** Particular models, completion setting, experts, and possible
training contamination; not an error-rate estimate for current harnesses.
**Application:** Treat generated or translated comments as drafts. Verify
semantics, terminology, natural language, and valid comment syntax.

## Using this evidence

For a policy or broad audit, apply the mapped questions to actual code. State
which claims are observed, inferred, or unknown. Do not treat this bibliography
as authorization to rewrite a repository or automatically apply a policy.
Ordinary source comments should explain the code, not recite this literature.

If extending the review, prefer primary full text, verify author/year and method,
record access limits, and distinguish a paper's findings from your own inference.
Keep private source and infrastructure out of external queries. The original
Gommenter bibliography supplied the starting leads for R1-R3 and Go conventions;
this review expands and qualifies that foundation without modifying that skill.
